# axiom3d v2 (AI toolkit + reliability) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give models a scene calculator, a sandbox (dry runs and batches) and a numeric diff after every edit. Make feet hold their heading while planted, harden every tool, add a phone-friendly viewer, and add a kit for testing axiom3d with Haiku through Claude over MCP.

**Architecture:** Everything still flows through `axiom3d/api.py` `Workbench`. The calculator is an AST-whitelist evaluator in `protocol/calc.py`, and its variables live in `SessionState.variables`. A batch is one stored command (`{"op": "batch", "edits": [...]}`), so undo and replay stay one-step. Dry runs reuse the `_edit` pipeline and skip the commit. The viewer embeds the existing GLB in a three.js page.

**Tech Stack:** Python ≥3.11, numpy, Pillow, mcp 2.x; dev: pytest, hypothesis; viewer: three.js 0.160.0 (jsdelivr).

**Spec:** `docs/superpowers/specs/2026-10-24-axiom3d-v2-design.md` (v1: `docs/superpowers/specs/2026-10-24-axiom3d-design.md`)

## Global Constraints
- The runtime dependencies stay exactly `numpy`, `Pillow`, `mcp>=2.3,<3`. `hypothesis` is added to the dev group only.
- Never `eval` or `exec` model input. The calculator walks Python `ast` nodes against a whitelist.
- Exactly 15 MCP tools: the 13 from v1 plus `calc` and `batch`. `dry_run` is a parameter, not a tool.
- Every model-facing failure is an `AxiomError`. Any other exception that reaches MCP or the CLI becomes `INTERNAL ERROR (please report): <Type>: <msg>` (CLI exit code 2).
- The v1 conventions, track frame and protocol rules are unchanged unless a task says otherwise.
- three.js is pinned at `three@0.160.0` from `https://cdn.jsdelivr.net/npm/`.
- Commit after every task on `claude/vigilant-goodall-y4x0bf`, with the session trailer, and push after each milestone.

## Review Focus
1. **Hostile calculator input:** `__import__('os')`, `x.__class__`, a lambda or comprehension, `9**9**9`, nesting 200 levels deep, a 10k-character string. Each must raise `CalcError` quickly and never execute anything. Pinned in Task 1.
2. **Dry runs on an invalid edit,** while a discrepancy is pending, or after DONE: clear messages, and the session file's bytes never change. Pinned in Task 4.
3. **A batch whose third edit is invalid:** nothing is applied, and the message names edit #3. Pinned in Task 4.
4. **A v1 session file** with no `version`, `variables` or new ledger keys: it loads and keeps working. Pinned in Task 6.
5. **Two HTTP MCP connections at once:** each gets its own session; neither sees nor edits the other's. Pinned in Task 10.

### Task 1: Scene calculator core

**Files:** Create `axiom3d/protocol/calc.py`. Test: `tests/test_calc.py`.

**Interfaces:**
- Consumes: `measure.track_coords`, `conventions.character_axes` / `track_to_world`, `FrameState.points` / `angles` / `root_position` / `heading_deg`, `skel.dims`.
- Produces:
  - `CalcError(ValueError)`
  - `@dataclass CalcResult(lines: list[str], assigned: dict[str, float | list[float]])`
  - `run_calc(source: str, skel, clip, states, variables: dict) -> CalcResult`. It doesn't mutate `variables`; the caller merges `assigned`.

**Language:**
- Statements are separated by `;` or newlines. A statement is an expression or `name = expression`.
- Names must match `[a-z_][a-z0-9_]*` and must not shadow a constant, point, joint or function.
- Values are floats or 3-vectors (numpy). `[a, b, c]` is a vector literal; `v.x/.y/.z` reads a component.
- **Scene references:**
  - A point name gives its world position at the last frame.
  - `<ref>@<int expr>` reads at a frame. The `@` is Python MatMult with a scene reference on its left; any other MatMult raises "@ means 'at frame'".
  - `left_hip.flexion` (a channel), `root.heading|x|y|z|forward|left|height`, and `left_toe.z@12` all work. A frame outside the timeline raises `CalcError` naming the range.
- **Functions:** `dist`, `angle(a, b, c)` (degrees, at b), `vec(a, b) = b - a`, `dot`, `cross`, `norm`, `unit`, `proj(v, axis)` (scalar), `lerp`, `clamp`, `sin`/`cos`/`tan` (degrees), `asin`/`acos`/`atan2` (degrees out), `sqrt`, `abs`, `min`, `max`, `round(x, n=0)`.
  - **Frame conversions:**
    - `track(p) -> [forward, left, z]`
    - `char(v, frame) -> [forward, left, up]` of a world vector at that frame's heading
    - `world_from_track([f, l, z])`
  - **Reach helpers:**
    - `reach(h) = sqrt(max(0, leg² - (h - ankle_height)²))`
    - `knee_needed(h, horizontal) = 180 - acos((a² + b² - L²) / 2ab)` in degrees, where `L = sqrt(horizontal² + (h - ankle_height)²)`; if L > leg it raises `CalcError("unreachable: short by X m")`
- **Constants:** `thigh`, `shank`, `leg`, `ankle_height`, `pelvis_height`, `hip_half_width`, `foot_length`, `fps`, `start`, `end`, `pi`, `FORWARD0`, `LEFT0`, `UP`.
- **Limits:** source ≤ 500 characters, AST depth ≤ 40, `**` exponent ≤ 10 in magnitude, every result ≤ 1e6 in magnitude (vectors too), at most 50 variables in total.
- **Output:** lines like `stride = 0.360` or `= [0.088, -0.360, 0.068]`, with 3 decimals.

### Task 3: Numeric diff after every edit

**Files:** Create `axiom3d/perceive/diff.py`. Modify `api._edit`. Test: `tests/test_diff.py`.

**Interfaces:**
- `describe_diff(skel, kind, before: (clip, states), after: (clip, states), frame: int, limit: int = 12) -> list[str]`
- The first line is `CHANGED:`, or `CHANGED: nothing measurable` for a no-op.
- **Lines, in this order:**
  1. root track forward / left / height / heading at `frame` (changes > 0.005 m or 0.5°)
  2. `KEY_POINTS = (pelvis, head_top, left_ankle, right_ankle, left_toe, right_toe, left_hand, right_hand)` track (forward, left) and z at `frame`

  4. channels changed > 0.5° at `frame`
  5. `checks: FIXED a, b; NEW c` (error ids before vs after)
- Beyond `limit` lines, it appends `(+N more)`.
- `_edit` appends these lines after the predictions block.

### Task 4: Sandbox (dry runs and batches)

**Files:** Modify `axiom3d/anim/commands.py` (op `batch`), `axiom3d/api.py`, `axiom3d/protocol/ledger.py`, `axiom3d/session_store.py` (`sandbox_seen: list[str] = []`), `axiom3d/mcp_server.py`. Test: `tests/test_sandbox.py`.

**Interfaces:**
- `apply_command` accepts `{"op": "batch", "edits": [cmd, ...]}`:
  - 1–40 edits, no nested batch
  - applied in order to one copy
  - a `CommandError` in edit i is re-raised as `CommandError(f"batch edit #{i+1} ({op}): {msg}")`, and nothing is applied
- **Default prediction frame:** for a batch, `_prediction_frame` returns the default frame of its last edit.
- **dry_run:** every edit method (`set_root`, `set_pose`, `plant_foot`, `swing_foot`) and the new `Workbench.batch(edits: list[dict], expect=None, dry_run=False, session=None)` take `dry_run: bool = False`.
- **`_edit(cmd, expect, session, dry_run)` rules:**
  - DONE → error. BRIEFING → error (protocol).
  - A pending discrepancy blocks only non-dry edits.
  - The expect, precision and relevance gates apply to dry runs as well.
  - **Dry run:** prepends `DRY RUN: nothing changed. To apply, repeat the call with dry_run=false.`, does not append the command, never sets `pending_discrepancy`, increments `ledger["dry_runs"]`, counts predictions like a real edit, and stores `sha256(json.dumps(cmd, sort_keys=True))` in `st.sandbox_seen` (keeping the last 50).

  - **Batch:** increments `ledger["batches"]`.
- `new_ledger` gains `dry_runs: 0` and `batches: 0`.
- MCP tool `batch(edits: list[dict], expect: list[str] | str | None = None, dry_run: bool = False)`. The four edit tools gain `dry_run: bool = False`.

### Task 5: Planted feet hold their heading

**Files:** Modify `axiom3d/anim/clip.py` (`Plant.yaw_deg: float | None = None`), `axiom3d/anim/commands.py` (plant `facing`), `axiom3d/rig/ik.py`, `axiom3d/anim/evaluate.py`, `axiom3d/checks/gait.py`, `axiom3d/tasks/library.py`, `axiom3d/tasks/reference.py`, and `api.plant_foot` / MCP (`facing=None`). Tests: `tests/test_ik.py`, `tests/test_clip.py`, `tests/test_checks.py` (append).

**Interfaces and rules:**
- `solve_leg(..., foot_yaw_deg: float | None = None)`: the pole is the forward vector at `foot_yaw_deg` (the knee goes over the toes), and the foot-flat target is `heading_quat(foot_yaw_deg)`. `None` means the body heading (the v1 behaviour).
- **Plant yaw:** `facing` is a world heading in degrees, bounded ±720. With no facing, a plant's yaw is resolved **live** as the root heading at `plant.start`, which keeps command order irrelevant (see v1's I7 fix).
- **Swing yaw** interpolates linearly between its two plants' yaws.
- `gait.foot_slide` measures drift as the max over ankle, heel and toe xy.
- **step_direction exemption:** a swing whose foot yaw changes by more than 20° (a turning step) is exempt from both the share rule and the backswing rule. It is still bound by laterality and the joint limits.
- Hip internal rotation (±40°) now absorbs the difference between the body heading and the foot yaw. The existing joint-limit check, with a new hint for internal_rotation ("planted feet keep their heading: turn with step-turns of ≤ 40° per step"), catches pivots.
- **`_step_length` criterion** uses the **last** swing window of that foot (the final step), not the first.

**New `turn_then_step` reference** (world positions converted to track: forward = -y, left = x):
- **Root:**
  - set_root f0 heading 0 height 0.92; f8 heading 35; f14 heading 35; f20 heading 75
  - set_root f24 heading 90 height 0.92 left 0; f28 height 0.92; f32 height 0.885
  - set_root f36 left 0.18 height 0.885
- **Feet:**
  - pf right 0..14; pf left 0..8; sw left 8..14
  - pf left 14..24 forward -0.0822 left 0.0299 facing 70
  - sw right 14..20; pf right 20..36 forward 0.0875 left 0 facing 90
  - sw left 24..32; pf left 32..36 forward -0.0875 left 0.36 facing 90
- These numbers were hand-checked so every |heading − planted yaw| ≤ 35° and every IK target is reachable. If a test shows otherwise, adjust the timing or positions; never loosen a check.
